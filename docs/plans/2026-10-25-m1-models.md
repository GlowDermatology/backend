## 2. Layering (import-linter `layers` contract; plan §4.1)

A module imports only strictly lower layers; siblings never import each other; FKs are string references and do
not count as imports.

```
reporting | customers                       ← selectors + admin API only, no tables
notifications                               ← StatusTemplate, CustomerSegment, SegmentMember, Campaign, CampaignRecipient, InboxNotification
commerce | appointments                     ← Cart, CartItem, Order, OrderItem, OrderEvent, StockReservation | Appointment, AppointmentEvent
payments | delivery | loyalty | catalog | professionals
         Payment, Refund | Shipment, ShipmentEvent | CashbackPolicy, CashbackTier, LoyaltyAccount, LedgerEntry,
         CashbackHold, Purchase, PurchaseItem, PosDevice | Category, Product, ProductStock, ProductImage, Banner |
         Location, Professional, Service, ProfessionalService, WorkingHours, WorkingHoursOverride, BlockedPeriod
site_config                                 ← SiteSettings
accounts                                    ← Customer, Device, Address, SmsCode, CustomerSocialIdentity, (StaffUser, AuthSession, SocialIdentity from M0)
integrations                                ← WebhookInbox, Job, IntegrationState
core                                        ← AuditEntry, OutboxMessage, IdempotencyRecord (M0)
```

Rules applied uniformly in all three files (each §0):

- The upper module owns the transaction; lock order **Order → Payment → LoyaltyAccount** (a flow may skip a level,
  never go back). `LoyaltyAccount.balance` changes only in `loyalty.services.post_entry()`.
- **Lower-layer services take scalar ids/values** (`order_id`, `customer_id`, amounts), never an upper-layer model
  instance (`create_hold(*, customer_id, order_id, amount, expires_at)`, `capture_hold(order_id)`,
  `record_online_purchase(*, customer_id, order_id, items_subtotal, promo_subtotal, cashback_used, at, items,
  billz_order_uuid=None)`, `reverse_purchase(order_id)`, `ensure_shipment(order_id)`,
  `request_bts_create(order_id, *, manual, actor_id)`).
- **Layer reads**: a lower module's selector may traverse its *own* FK upward (`Shipment.order__status`,
  `Payment.order__customer__phone`) but never a reverse relation into an upper table (`catalog` never reads
  `commerce_stockreservation`; `available_stock` is `commerce.selectors`).
- Actor FKs to `accounts.StaffUser`: `PROTECT` on append-only rows and business rows; `SET_NULL` on
  configuration/content rows (`Product.last_change_actor`, `ProductImage.uploaded_by`, `SiteSettings.updated_by`,
  `WorkingHoursOverride/BlockedPeriod.created_by`, `StatusTemplate.updated_by`, `CustomerSegment.created_by`,
  `SegmentMember.added_by`).
- Append-only event tables (`LedgerEntry`, `ShipmentEvent`, `OrderEvent`, `AppointmentEvent`) carry the business time
  as `at`; `CashbackPolicy`/`CashbackTier` keep `created_at` (contract name); `WebhookInbox` has `received_at`.
- Contract enums come from `core/enums.py`; internal states are nested `TextChoices` on their model
  (01 §9, 02 §0.1, 03 §0.4).
- Money `BigIntegerField` so'm; percent `DecimalField(5, 2)` with integer basis-point math; `CharField` never
  `null=True`; every "now" default is `timestamp_default`; i18n text as `*_uz/_ru/_en` columns.

## 4. Outbox topic registry (03 §5; plan §4.2)

Handlers are `@outbox.register(topic)` in the orchestrating module's `tasks.py`, at-least-once, idempotent at the
provider boundary; `enqueue` is `get_or_create(dedupe_key)`.

| Topic | Producer | Handler | `dedupe_key` | Provider-boundary guard |
|---|---|---|---|---|
| `bts.create_shipment` | `commerce.confirm_payment_effects` / `commerce.retry_shipment` via `delivery.services.request_bts_create` | `commerce/tasks.py` → `delivery.services` + `integrations.bts` | `bts.create_shipment:{order_id}:{request_no}` | skip if order not `processing` or shipment `created`; BTS lookup by `clientId = order_id` before create; `Shipment` 1:1 |
| `bts.cancel_shipment` | synchronous call inside `cancel_order` — **not an outbox topic** | — | — | the BTS answer decides the cancel transaction (409/503 before any write) |
| `billz.push_sale` | `commerce.confirm_payment_effects` | `commerce/tasks.py` → `loyalty.services.link_billz_sale` + `integrations.billz` | `billz.push_sale:{billz_order_uuid}` | `Purchase.billz_order_uuid` persisted before the message; skip when `billz_pushed_at` set; one `billz_sale_recorded` event per order |
| `refund.submit` | `payments.services.create_refund` (Click only, from `cancel_order`) | `commerce/tasks.py` → `payments.services.mark_*` + `integrations.click` | `refund.submit:{refund_id}` | `mark_submitting` committed before the call; status check by `provider_txn_id` before any reversal; `unknown` never auto-retried; dead letter → `failed (dead_letter)` |
| `push.order_status` | `commerce.services` (status rows of 03 §4.1) | `notifications/tasks.py` → `deliver_order_status` + `integrations.fcm` | `push.order_status:{order_id}:{status}` | `InboxNotification.dedupe_key = order_status:{order_id}:{status}` + claim protocol |
| `push.appointment` | `appointments.services.confirm/reject` (+ reschedule, admin cancel — A-3) | `notifications/tasks.py` → `deliver_appointment` + `integrations.fcm` | `push.appointment:{appointment_id}:{action}` (`…:rescheduled:{n}`) | `InboxNotification.dedupe_key = appointment:{id}:{action}` + claim protocol |
| `campaign.send_batch` | `notifications.services.create_campaign` / beat `start_due_campaigns` / the handler (next batch) | `notifications/tasks.py` → `send_batch` + `integrations.fcm` | `campaign.send_batch:{campaign_id}:{batch_no}` | `CampaignRecipient` unique `(campaign, customer)`/`(campaign, device)`, processed from `pending` after `send_cursor`; batch *n+1* enqueued after *n* committed |
| `sms.send` (M2) | `accounts.services.send_code` | `accounts/tasks.py` → `integrations.eskiz` | `sms.send:{sms_code_id}` | `SmsCode.sent_at` claimed before the Eskiz call; no resend once set |

Dead letters (`dead` after 10 attempts, audit `outbox.dead`): `commerce.tasks.on_outbox_dead` (registry in
`core.outbox`, X-1) marks a `bts.create_shipment` shipment `failed (dead_letter)` + `shipment_failed` event, and a
`refund.submit` refund **`failed (dead_letter)`** + `refund_failed` event; other topics only audit.

Beat entries owned by M1: `core.dispatch_outbox` (10 s), `commerce.expire_reservations` (1 min),
`notifications.start_due_campaigns` (1 min), `commerce.poll_bts` (10 min, M2/M3), `integrations.reap_stale_jobs`
(5 min), `loyalty.reconcile_balances` (03:30), `reporting.consistency_report` (03:40).

## 5. Review log

The adversarial review ([REVIEW.md](m1-models/REVIEW.md)) checked the three section files line by line against the
contract, the spec sections, the plan §4/§5.3, `core/*`, `accounts/models.py` and the installed Django 6.1.2
sources. It confirmed the model set is complete against the contract (every response field, filter and export
column has a column or an SQL-level derivation; all seven spec uniques exist; no `SET_NULL`/`CASCADE` touches an
append-only table; the №10248 history vector and Malika's ledger/totals reproduce exactly) and returned
**2 blockers, 5 majors, 17 minors — verdict REVISE**. Every item was applied in the fix pass; none was rejected.

### Blockers

| # | Finding | Resolution |
|---|---|---|
| 1 | `GinIndex`, `ExclusionConstraint`, `DateTimeRangeField` fail system check `postgres.E005` because 01 §7 and 03 §2.1 kept `django.contrib.postgres` out of `INSTALLED_APPS` | **Fixed.** `django.contrib.postgres` is installed (01 §6.1, §7; 03 §2.1, §9, §10, A-1 closed); `core.0007` uses `TrigramExtension()`; the contrary sentences are deleted; the ORM `ExclusionConstraint` stays. |
| 2 | `GinIndex(Lower("name"), opclasses=[…])` raises `ValueError` at import (`Index.opclasses cannot be used with expressions`); `Lower` not imported | **Fixed.** 01 §1.1 now `GinIndex(OpClass(Lower("name"), name="gin_trgm_ops"), name="accounts_customer_name_trgm")` with the imports; emitted SQL documented. |
